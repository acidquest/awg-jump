# Задержки API и ложное отсутствие в Home Assistant — 15 октября 2026

## Причины по коду

Интеграция при ошибке запроса подменяла последнее присутствие синтетическим
`is_present=false`. Теперь она сохраняет последнее подтверждённое состояние,
публикует у трекера `stale_due_to_error=true` и снимает этот признак после
успешного ответа. Повторные ошибки также сохраняют присутствие и исходные
временные метки. Без первого успешного ответа обновление завершается ошибкой.

На шлюзе асинхронные задачи напрямую выполняли блокирующие операции:

- обнаружение устройств: `ip neigh`, `conntrack`, последовательные ping и
  `socket.gethostbyaddr`;
- проверки узлов в failover и HTTP-обработчиках: ping и UDP;
- обновление внешнего IP: два последовательных curl с лимитом по 10 секунд;
- сбор трафика и определение состояния туннеля: системные команды.

Ожидание этих операций блокировало общий цикл asyncio и обработку HTTP.
Цикл обнаружения устройств ждёт 30 секунд **после завершения** сбора.
Если сбор занимает 24–27 секунд, период составляет 54–57 секунд, как в отчёте.
Это наиболее подходящий кандидат по коду, но конкретный источник задержки
на целевом сервере без его трассировки не установлен.

Дополнительный риск: фоновые проверки внешнего IP и отправка статуса удерживали
соединения с основной БД во время сети. При стандартном пуле из двух соединений
это могло задерживать авторизацию API даже после освобождения цикла asyncio.

## Исправления шлюза

Перечисленные сетевые проверки и чтение счётчиков вынесены через
`asyncio.to_thread`. Работа с сессиями БД и запись результатов остаются в
асинхронных функциях. Фоновые проверки внешних сервисов возвращают соединения
в пул до сетевого ожидания. В лог обнаружения устройств добавлен
`duration_seconds`, позволяющий сопоставить длительность сбора с периодом сбоев.

## Проверка

- Интеграция: 28 тестов прошли, включая повторные ошибки, четыре типа ошибок,
  сохранение присутствия/отсутствия, восстановление и атрибут устаревания.
- Шлюз: 110 тестов прошли, 2 проверки в `test_routing_plan.py` упали.
  Оба падения воспроизведены на исходных файлах HEAD отдельно от изменений:
  ожидание команды `ip rule add fwmark 0x1 table 200`.
- Восемь новых тестов проверяют обработку HTTP при удерживаемых сетевых
  проверках; пять из них запрашивают настоящий `/api/access/devices?scope=marked`
  с отдельной временной SQLite-БД во время сбора устройств.
- Компиляция Python и `git diff --check` проходят.

## Граница проверки и применение

Изменения подготовлены в исходниках. Целевые службы HA и шлюза не обновлялись
и не перезапускались. Тесты используют ASGI в процессе и имитируют медленную
сеть; они не подтверждают устранение тайм-аутов на целевом сервере.

После установки интеграции и пересборки/перезапуска шлюза нужно повторить
опрос из HA за несколько циклов и сопоставить его с `duration_seconds` в логах.
Долгие операции запуска/остановки туннеля, применения firewall, DNS и архивации
не стали полностью асинхронными в рамках этого исправления. Сами проверки
устройств остаются последовательными: исправление позволяет обслуживать API
во время их ожидания, но не гарантирует сокращение длительности сбора.
